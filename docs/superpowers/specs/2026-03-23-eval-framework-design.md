# RAG Evaluation Framework — Design Spec

**Date:** 2026-03-23
**Status:** Approved for implementation

---

## Overview

Add a retrieval evaluation framework that measures Recall@5 and MRR across four retrieval strategies: BM25-only, kNN-only, Hybrid (BM25+kNN via weighted RRF), and Hybrid+Rerank. The output is a comparison table with real numbers (e.g. "Hybrid+Rerank achieved 92% Recall@5 vs 71% for BM25-only") that demonstrates intentional measurement of the RAG pipeline.

## Ground Truth Dataset

### Schema

```json
[
  {
    "id": "q01",
    "query": "我的孩子能申请CHIP吗",
    "queryType": "eligibility",
    "docId": "PLACEHOLDER_CHIP_DOC_ID",
    "relevantChunks": [
      { "chunkIndex": 3 },
      { "chunkIndex": 4 }
    ]
  }
]
```

- `docId` at the query level is the single document searched (matches production behavior — chat is always document-scoped)
- `relevantChunks` lists the correct passage(s) by `chunkIndex` within that document
- `queryType` is **metadata only** — it is not consumed by `run-eval.js`; it exists to document coverage intent

**Stability constraint:** `chunkIndex` values are stable as long as `CHUNK_SIZE`, `OVERLAP`, and the source document text are unchanged. If chunking parameters are modified, ground-truth labels must be re-verified.

## Retrieval Strategy Variants

### Return Shape (all four strategies)

```js
{ chunkId, content, chunkIndex, title, source, url }[]
```

- `chunkIndex` is **not currently returned** by `retrieveChunks` — this is a **required code change that must be implemented before `run-eval.js` will produce correct results**. Without it, every `results[i].chunkIndex` will be `undefined`, causing all Recall@5 and MRR scores to read 0. The data is already present in `candidateMeta[r.index].chunkIndex` (tracked at lines 85/97 in `ragService.js`); it just needs to be forwarded in the return object: `chunkIndex: candidateMeta[r.index]?.chunkIndex`.
- `url` is always `null` in the current implementation (ES index has no url field yet). It is included for forward compatibility.
- This is backward-compatible for existing callers (`agenticPipeline.js`, `chatService.js`) — they ignore unknown fields.

### All four variants must include the `doc_id` filter

Every ES query (BM25, kNN, or both) must include `filter: [{ term: { doc_id: documentId } }]` to scope results to a single document. This is required for correct eval comparisons (same search space across all strategies) and matches production behavior.

### `retrieveChunksBM25Only(query, documentId)` [new]
- Translate Chinese query to English (same as `retrieveChunks`)
- Run BM25 `multi_match` search with `doc_id` filter, `size: TOP_K` (5) — no fusion step, so fetch only what you need
- Return top-5 by BM25 score
- **Does NOT call the embedding service** — runnable without port 8001

### `retrieveChunksKNNOnly(query, documentId)` [new]
- Embed original query via embedding service (port 8001)
- Run kNN vector search with `doc_id` filter, `size: TOP_K` (5)
- Return top-5 by cosine similarity
- No translation, no BM25, no reranker

### `retrieveChunksHybridOnly(query, documentId)` [new]
- Run BM25 + kNN in parallel with `doc_id` filter, `size: SEARCH_SIZE` (20) each
- Apply weighted RRF fusion — **must use the exact same formula as `retrieveChunks`**:
  ```js
  // idx is 0-based (forEach callback index)
  fusionScore[hit._id] += WEIGHTS.fulltext / (idx + RRF_K)  // BM25
  fusionScore[hit._id] += WEIGHTS.semantic / (idx + RRF_K)  // kNN
  // WEIGHTS = { fulltext: 0.4, semantic: 0.6 }, RRF_K = 60
  ```
  Note: `idx` is **0-based** (the `forEach` index, not 1-based rank). First hit denominator is `0 + 60 = 60`, second is `1 + 60 = 61`, etc.
- Slice fused results to `TOP_K` (5) — **no reranker**

### `retrieveChunks(query, documentId)` [updated]
- Unchanged pipeline: hybrid RRF → cross-encoder reranker → top-5
- **Updated**: add `chunkIndex: candidateMeta[r.index]?.chunkIndex` to the return object

## Eval Runner (`eval/run-eval.js`)

### Prerequisites by Strategy

| Dependency | BM25 only | kNN only | Hybrid only | Hybrid+Rerank |
|---|---|---|---|---|
| Elasticsearch (9200) | ✓ | ✓ | ✓ | ✓ |
| Embedding service (8001) | ✗ | ✓ | ✓ | ✓ |
| Reranker service (8002) | ✗ | ✗ | ✗ | ✓ |
| Seeded docs + resolved docIds | ✓ | ✓ | ✓ | ✓ |

### Algorithm

```js
// Recall@5 is BINARY per query: 1 if any relevant chunk appears in top-5, else 0.
// MRR scores 1/rank of the FIRST relevant hit; subsequent relevant chunks are ignored.

for (const strategy of strategies) {
  let recallHits = 0;
  let reciprocalRankSum = 0;

  for (const q of groundTruth) {
    const results = await strategy.fn(q.query, q.docId);  // returns top-5

    for (let i = 0; i < results.length; i++) {
      const rank = i + 1;  // 0-based index → 1-based rank for 1/rank
      const isRelevant = q.relevantChunks.some(
        rc => rc.chunkIndex === results[i].chunkIndex
      );
      // No docId check needed — strategy.fn already filters by q.docId
      if (isRelevant) {
        recallHits += 1;           // binary: count query once regardless of how many relevant chunks match
        reciprocalRankSum += 1 / rank;
        break;                     // score only first hit; stop scanning remaining results
      }
    }
  }

  strategy.recall5 = recallHits / groundTruth.length;
  strategy.mrr     = reciprocalRankSum / groundTruth.length;
}
```

## Metrics Definitions

**Recall@5 (binary):** For each query, 1 if at least one relevant chunk appeared in the top-5 results, else 0. Averaged across all queries. Position within top-5 does not matter; multiple relevant chunks in top-5 still count as 1.

**MRR (Mean Reciprocal Rank):** Mean of `1/rank` of the first relevant chunk across all queries. Rewards systems that surface relevant chunks near the top.

| First hit at rank | MRR contribution |
|---|---|
| 1 | 1.00 |
| 2 | 0.50 |
| 3 | 0.33 |
| 4 | 0.25 |
| 5 | 0.20 |
| not found | 0.00 |

## Seeder Update (`scripts/seedDocs.js`)

After inserting all 4 documents, write `eval/seed-doc-ids.json` using the title-to-key mapping above.

The seeder is run from `node-backend/` (`node scripts/seedDocs.js <username>`), so relative paths resolve to `node-backend/eval/`, not the project root. Use an absolute path anchored to `import.meta.url`:

```js
import { fileURLToPath } from 'url';
import path from 'path';
import fs from 'fs';

const __dirname = path.dirname(fileURLToPath(import.meta.url));
const evalDir = path.resolve(__dirname, '../../eval');
fs.mkdirSync(evalDir, { recursive: true });
fs.writeFileSync(
  path.join(evalDir, 'seed-doc-ids.json'),
  JSON.stringify(docIdMap, null, 2)
);
```

This writes to `<project-root>/eval/seed-doc-ids.json` regardless of working directory.
